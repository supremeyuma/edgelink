# Redirect benchmark — local Miniflare

**Caveat:** these are `wrangler dev` (Miniflare) numbers on the development laptop, not edge
measurements. They show the shape of the tradeoff, not production latency. Deployed numbers
should replace the headline once a Cloudflare account is available.

Generated by `pnpm bench` (`scripts/bench.ts`) against `wrangler dev --port 8787`.

## Method

- **Cold:** create 300 unique links through the admin API, then request each slug exactly once
  with 20-way concurrency. Every request takes the D1 lookup path, warms KV via
  `ctx.waitUntil`, and performs the atomic `UPDATE … RETURNING` that enforces cap/expiry and
  increments clicks.
- **Warm:** create one link, warm it, then run autocannon for 8 seconds with 10 connections.
  A separate 100-request probe records the `X-Cache` header distribution.
- Both modes use `redirect: manual` so a 302 is measured rather than its destination.

## What the numbers mean

- The cache removes the D1 **read**, not the D1 **write**. Every redirect still executes the
  atomic counter update because that is the only safe way to enforce `max_clicks`. Warm
  latency is therefore bounded by D1 write latency, not by KV.
- Cold requests are dominated by D1 writes queueing under 20-way concurrency in a single
  Miniflare process. This is a local artifact; a deployed Worker fans out across isolates and
  D1 regions.
- `X-Cache: HIT` proves the versioned read path works; the benchmark does not claim that
  caching alone makes the redirect fast.

## Reproduce

```powershell
pnpm migrate:local
pnpm dev            # terminal 1, port 8787
pnpm bench          # terminal 2
```
